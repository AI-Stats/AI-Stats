# Tool calling and structured outputs: provider reference audit

Date checked: 2026-08-03

## What was checked

This is a reference-to-implementation audit, not an inference from Phaseo's generated provider mocks. For every registered production `text.generate` provider ID, the review:

1. followed the provider's current first-party API reference or product documentation;
2. checked native tool definitions, tool choice, tool-result continuation, parallel/streaming behaviour, JSON object mode, and schema-constrained output;
3. compared the documented wire shape and restrictions with the registered executor;
4. accounted separately for aliases and regional registrations, while reusing the same reference only where the code reuses the same vendor transport.

"Schema" below means an API-level JSON Schema constraint. Prompting a model to imitate a schema is not counted as native structured-output support. "Conditional" means support is model, endpoint, backend, region, or feature dependent. "Not established" means the first-party material checked did not document the capability; it does not mean the provider definitely lacks it.

## System-level finding

The production IR correctly represents tools, tool calls, tool results, tool choice, parallel calls, JSON object mode, and JSON Schema output across Chat Completions, Responses, and Messages. Response normalisation also handles streamed and buffered tool calls.

The weak point is the provider boundary:

- Most registered providers use the shared OpenAI-compatible executor and forward OpenAI shapes unless a provider quirk happens to exist.
- `sync-reference-overlays.mjs` copies OpenAI's complete request schema for a provider after establishing only broad OpenAI compatibility. Those generated contracts therefore cannot prove individual parameter support.
- `applyJsonSchemaFallback` silently changes an unsupported `json_schema` request into `json_object` plus a prompt instruction. That is useful best-effort compatibility, but it is not strict structured output and must not be advertised as such.
- Capability validation is only as accurate as route metadata. It cannot protect a request when metadata overstates the provider/model capability or omits a documented combination restriction.

## Provider-by-provider matrix

Verdicts:

- **Aligned** — the documented wire shape is compatible with the executor for the audited features, subject to route metadata naming supported models.
- **Conditional** — the common wire shape works only for documented models/endpoints/backends or with combination restrictions that route metadata must express.
- **Mismatch** — the executor emits or promises a materially different shape/guarantee.
- **Unverified** — no sufficiently detailed current first-party inference reference was located; OpenAI compatibility alone is insufficient evidence.
- **Invalid registration** — the referenced product does not expose the registered text-generation capability.

## Confirmed discrepancies

The audit found issues that the executor matrix cannot detect because its provider mocks accept reconstructed OpenAI schemas:

1. **Strictness is overstated.** The shared JSON Schema fallback is prompt instruction plus JSON object mode. It must be represented as best effort, not `structured_outputs`.
2. **Combination constraints are not represented.** Venice disallows parallel tool calls with structured responses; Cloudflare schema mode does not stream; xAI restricts combined tools and schemas to supported Grok 4 models.
3. **Provider-native shapes are missing.** Cohere strict tools/schema placement, NVIDIA backend-specific constrained generation, Anthropic native output format, and Mistral tool-choice semantics need provider transforms or explicit rejection.
4. **Model/endpoint scope is flattened.** Reka, Featherless, Baseten, Cloudflare, DeepInfra, Groq, Fireworks, Together, W&B, and several hosting platforms document model-dependent support.
5. **Two registrations lack a substantiated product contract.** Voyage/VoyageAI have no published text-generation endpoint; Akash's stored reference is a network API, not hosted inference.
6. **The generated contract provenance is misleading.** A copied OpenAI schema is a test fixture baseline, not a reference-derived provider contract.

## Required implementation guardrails

- Split route capabilities into at least native tool calling, native JSON object mode, native JSON Schema, streaming-with-tools, streaming-with-schema, parallel tools, and tools-plus-schema.
- Store evidence at provider-model-endpoint granularity, including the checked URL and date.
- Reject unsupported strict-schema requests or route them elsewhere; never silently satisfy a strict request with a prompt fallback.
- Apply provider-specific request transforms where the official wire shape differs.
- Make the generated mocks consume the audited capability manifest and reject unsupported combinations.
- Remove `voyage` and `voyageai` from `text.generate` until a first-party text-generation contract is supplied.
- Keep FAQ answers tied to active route metadata, but define “structured outputs” as native schema enforcement; best-effort JSON/prompt fallback must not make the answer “Yes”.
